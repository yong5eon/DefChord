# CI 실패 재현과 수정 검증

[실패 작업](https://github.com/yong5eon/DefChord/actions/runs/40942782687/job/123692320265?pr=26)의 로그를 확인했다. 패키징 단계가 아니라 설치된 제품의 어댑터 테스트에서 실패했다.

- Python 3.9: Uvicorn mock 경로가 모듈 대신 Server 클래스를 가리켜 `startup` 속성 부재 오류 1개, Gunicorn의 예전 배너 문구 검증 실패 4개
- Python 3.13: 같은 Gunicorn 배너 검증 실패 4개

Windows의 새 Python 3.9 검증 가상환경에 직전 일반 코어·어댑터 wheel을 설치하고 Uvicorn 테스트의 같은 `AttributeError`를 재현했다. Linux Python 3.13 컨테이너에서는 수정 전 테스트로 Gunicorn의 네 실패를 재현했다.

수정 후 저장소 루트 기준 테스트 진입점은 다음과 같다.

```shell
python -m unittest discover -s tests -p test_adapters.py
python -m unittest discover -s tests -p 'test_*.py'
```

| 검증 환경 | 결과 |
| --- | --- |
| Windows Python 3.9 일반 wheel, 어댑터 테스트 | 19개 실행, 통과(2개 건너뜀) |
| Windows Python 3.9 일반 wheel, 전체 제품 테스트 | 253개 실행, 통과(5개 건너뜀) |
| Linux Python 3.9 일반 wheel, 전체 제품 테스트 | 253개 실행, 통과(3개 건너뜀) |
| Linux Python 3.13 일반 wheel, 전체 제품 테스트 | 253개 실행, 통과(3개 건너뜀) |

Linux 검증은 공식 `python:3.9-slim`, `python:3.13-slim` 컨테이너에서 수행했다. 저장소는 읽기 전용으로 연결하고 컨테이너 임시 디렉터리에 테스트·샘플·소스를 복사했으며 제품은 일반 wheel로 설치했다. 처음 Linux 전체 테스트 실행은 보조 복사본에 샘플·소스가 없어 실패했으나 제품 수정 없이 필요한 참조 디렉터리도 복사한 뒤 재실행해 통과했다. 컨테이너는 실행 후 자동 제거했다. Debian WSL에는 Python이 없어 그 환경은 사용하지 않았다.

실제 Gunicorn의 sync·gthread·클래스 기반 작업자와 네 호출 형태를 Linux에서 검사했다. gevent 선택 테스트는 의존성이 없어 건너뛰었다. 전체 지원 버전의 원격 CI 재통과는 아직 확인하지 않았으며 이 기록 시점에는 추가 커밋·푸시를 하지 않았다.
