# 요구사항

## 분석

- 현재 `Specifications.__call__`은 `ResponseJSON(self.document())`을 고정 사용하므로 JSON 외 형식을 선택할 수 없다.
- 이슈는 JSON 기본 동작 보존, YAML 응답 지원, Content-Type/UTF-8 일치, JSON/YAML 의미 동등성, 오류의 명시적 전파를 요구한다.
- OpenAPI 버전은 현재 문서 생성 코드가 `3.1.0` 문자열을 고정한다. 버전 확장 여부는 YAML 출력과 분리해 검토해야 한다.

## 확정 요구사항

- `Specifications`는 공개 API로 문서 응답 형식을 선택할 수 있어야 하며 기본값은 기존과 동일한 JSON이어야 한다.
- 지원 형식은 `json`, `yaml`로 제한하고 지원하지 않는 형식은 명시적 오류(`ValueError`)로 처리한다.
- YAML 응답은 UTF-8 바이트와 YAML 미디어 타입 Content-Type을 사용한다. YAML 본문을 JSON Content-Type으로 반환하지 않는다.
- JSON과 YAML은 동일한 `document()` 결과를 직렬화해야 하며 의미가 보존되어야 한다.
- 문자열·숫자·불리언·null·배열·객체와 비ASCII 문자열이 YAML 파싱 후에도 의미와 자료형이 유지되어야 한다.
- `paths`, `components`, `$ref`, 보안 정의, `x-defchord-*` 확장 필드가 YAML 출력에서도 보존되어야 한다.
- 문서 생성 실패와 YAML 직렬화 실패는 숨기거나 JSON으로 폴백하지 않고 기존 예외 흐름으로 전파한다.
- YAML 직렬화 의존성 정책은 선택 의존성(`PyYAML`)으로 두고, 형식 선택 방법과 설치 방법을 한국어/영어 상세 매뉴얼에 반영한다.

## OpenAPI 3.2 검토 결론

- 이번 변경 범위는 문서 직렬화 형식(JSON/YAML) 추가이며, OpenAPI 스키마 생성 로직 자체(3.1 고정 필드와 구조)를 3.2로 확장하지 않는다.
- OpenAPI 3.2 채택은 다음 검토가 필요하므로 이번 이슈에서는 보류한다.
- 검토 필요 항목:
  - DefChord 문서 생성 로직이 3.2에서 추가/변경된 필드와 규칙을 생성·검증할 수 있는지
  - 현재 연동 도구(`Swagger` UI 경로, 사용자 검증 파이프라인)에서 3.2 문서 소비를 실사용으로 검증할 수 있는지
  - 3.1 사용자와의 호환성(기본 버전, 선택 API, 다운그레이드/고정 정책)
- 결론적으로 지원 버전은 현재와 동일하게 `3.1.0`을 유지하고, YAML 출력은 3.1 문서에 대해 지원한다.

## 인수 기준

- 기본 설정에서 기존과 동일하게 JSON OpenAPI 응답을 받을 수 있다.
- 문서화된 선택 방법으로 YAML 응답을 받을 수 있고 Content-Type과 UTF-8 인코딩이 본문과 일치한다.
- 동일한 라우트 선언 기준 JSON과 YAML 파싱 결과가 동일하다.
- `paths`, `components`, `$ref`, 보안 정의, `x-defchord-*`가 YAML에서도 유지된다.
- 비ASCII 및 YAML에서 오인 가능한 문자열 값/키가 의미 보존된다.
- 잘못된 형식 선택, 문서 생성 실패, YAML 직렬화 실패가 명시적으로 드러나며 조용한 폴백이 없다.
- 기존 OpenAPI 생성·JSON 응답 동작 회귀가 없다.
- 한/영 상세 매뉴얼에 JSON/YAML 선택법과 설치 조건이 반영된다.
