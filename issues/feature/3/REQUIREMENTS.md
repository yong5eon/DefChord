# 로깅 지원 요구사항 명세서

## 1. 목적과 문서 상태

[로깅 지원 이슈](./ISSUE.md)의 “파편화된 로깅 정리”를 다음 두 요구로 구체화한다.

1. `DefEssential`을 최상위 로거 이름으로 사용하여 프레임워크 로그를 계층별로 선택할 수 있게 한다.
2. 애플리케이션 시작·종료, 요청 실행, 응답 전송, 확장 및 연결 실패를 추적하는 데 부족한 로그를 추가한다.

이 문서는 현재 소스와 DefStream의 로깅 방식을 분석한 **구현 전 요구사항 초안**이다. 아래 로거 배치와 기록 정책은 이번 이슈의 제안이며, 구현 완료나 사용자 승인 사실을 뜻하지 않는다. 이번 작업에서는 명세만 작성하고 소스 동작을 변경하지 않는다.

사용자 후속 의견에 따라 샘플의 출력 설정 위치는 Application 시작 훅으로 정한다. 출력 대상은 `Sample`·`DefEssential` 계층만이며, 포맷은 DefStream의 예제와 맞춘다.

## 2. 현황과 문제 분석

| 현재 상태 | 문제와 개선 방향 |
| --- | --- |
| 기존 로거는 이미 `DefEssential.Application`, `DefEssential.Server`, `DefEssential.RequestRunner`, `DefEssential.IO.WebSocket`, 일부 `DefEssential.Extensions.*` 이름을 사용한다. | 루트 이름이 전혀 없는 문제가 아니다. 기존 이름을 가능한 한 유지하면서 클래스 멤버와 책임 경계를 일관되게 정리한다. |
| 일부 클래스는 `logger` 멤버를 사용하고, 다른 곳은 오류 처리 중 `getLogger()`를 직접 호출한다. | 클래스의 프레임워크 로그는 명시적 클래스 멤버를 사용하고, 공통 함수는 담당 경계의 명시적 로거로 귀속한다. |
| Application은 주로 확장 정리 실패를 기록하며 시작·종료 성공, 라우팅, 요청 처리 단계는 충분히 관찰되지 않는다. | 생명주기는 INFO, 등록·라우팅·훅·실행 단계는 DEBUG로 보강한다. |
| Python 서버의 `log_message()`는 기본 HTTP 처리기의 메시지를 INFO로 출력한다. | 응답 헤더 생성 시점의 접근 기록을 실제 전송 완료로 오인할 수 있다. 공통 전송 결과와 중복되지 않게 정리하고 원시 요청 대상의 노출을 막는다. |
| 공통 요청 처리기는 예상하지 못한 요청 오류, 연결 단절, 전송·정리 실패를 기록한다. | 요청 식별자, 처리 단계, 응답 상태와 성공·실패의 대응을 보강한다. |
| 응답 본문 정리 공통 함수는 `DefEssential.RequestRunner`를 사용한다. | 기존 귀속을 유지하되 본문 정리 오류와 원래 처리 오류를 서로 다른 사건으로 구분한다. |
| 샘플은 `basicConfig()`와 `Sample` 로그를 사용하며, 요청 훅에서 원시 URI를 출력한다. | 샘플도 출처 필터와 안전한 요청 문맥을 사용하며, 훅 완료와 실제 전송 완료의 의미를 구분해야 한다. |
| 시작 배너는 별도 `print()`로 출력한다. | DefStream처럼 배너는 유지한다. 로깅 도입을 이유로 배너를 제거하거나 그대로 중복 기록하지 않는다. |

## 3. 범위와 기본 원칙

### LOG-01. 표준 logging과 설정 책임

- Python 표준 `logging`을 사용한다. 별도 로깅 라이브러리나 `LOG_*` 래퍼 API를 추가하지 않는다.
- 라이브러리는 로그만 기록한다. import, 인스턴스 생성, 시작·종료 중 `basicConfig()`, 핸들러, `NullHandler`, 포매터, 필터, 로그 레벨을 임의로 설정하지 않는다.
- 루트 로거로의 기본 전파를 막지 않는다. 애플리케이션이 이미 설정한 로거·핸들러·레벨·필터를 변경하거나 제거하지 않는다.
- 미설정 상태의 완전한 무출력은 보장하지 않는다. 핸들러가 없으면 표준 `logging.lastResort`에 의해 WARNING 이상이 stderr에 출력될 수 있다.
- Gunicorn·Uvicorn 자체 로그의 이름을 바꾸거나 강제로 `DefEssential`에 편입하지 않는다. 외부 서버의 로깅 설정은 기존 서버 옵션과 사용자 설정의 책임이다.

### LOG-02. 포함·제외 범위

포함 범위는 Application, 프레임워크가 호출하는 훅과 요청 실행, 내장 확장, 세 서버 어댑터, 응답 전송 및 WebSocket의 주요 상태 변화다. 공개 메서드·훅의 인자, 반환형, 호출 순서를 로깅 때문에 변경하지 않는다.

다음은 제외한다.

- 로그 파일 저장·회전·보관 기간, 외부 수집기 전송, JSON 전용 포맷
- 새 로깅 설정 API, 요청 추적 시스템, 외부 trace ID 전파 프로토콜
- 요청·응답 본문 덤프, WebSocket 메시지 및 SSE 이벤트 내용 기록
- 모든 자료형·검증기·descriptor·프레임의 재귀적 세부 로깅
- 자동 로그 샘플링·빈도 제한 시스템, 새로운 비동기 로깅 큐
- 로깅과 무관한 서버·라우팅·훅·예외 처리 계약 변경

## 4. 로거 이름과 소유권

### LOG-03. 명명·상속 규칙

- 모든 프레임워크 로거 이름은 `DefEssential` 또는 `DefEssential.`으로 시작한다. `getLogger(__name__)`로 설치 경로나 사용자 모듈에 따라 이름이 달라지게 하지 않는다.
- 로깅을 담당하는 클래스는 `logger` 클래스 멤버에 고정 이름을 선언하고 공통 메서드는 `self.logger`를 사용한다.
- 사용자 하위 클래스는 기반 클래스의 이름을 상속한다. `type(self).__name__`으로 자동 변경하지 않으며, 사용자가 `logger`를 명시적으로 재정의하는 것은 허용한다.
- 실제 사용자 핸들러·확장·훅의 식별은 `모듈명.정규 클래스명` 문맥으로 구분한다. 사용자 코드가 직접 호출하는 로깅은 변경하지 않는다.
- 함수에 로거를 전달하기 위한 새 공개 인자나 로그 이름 판별용 추상화를 추가하지 않는다.

RequestRunner와 Extension의 추상 훅 인터페이스에는 로깅을 위해 별도 동작을 추가하지 않는다. 호출 전후는 실행 주체가 기록한다. 응답 writer·reader, WSGI 전송·Uvicorn 연결 보조 객체의 모든 I/O에 독립 로그를 추가하지 않고, 공통 서버 경계에서 결과를 관찰한다.

`DefEssential`로 전체 로그를, `DefEssential.Extensions`로 내장 확장 로그를, 구체 이름으로 개별 구성요소를 선택할 수 있어야 한다.

## 5. 이벤트와 로그 레벨

### LOG-05. 공통 레벨

| 레벨 | 기준 |
| --- | --- |
| DEBUG | 요청별 실행 단계, 등록·라우팅·훅 호출, 확장 내부 처리 요약 |
| INFO | 실제 생명주기 변화와 HTTP 전송 결과 요약 |
| WARNING | 클라이언트 연결 단절, WebSocket 프로토콜 위반처럼 내부 장애와 구분할 주의 사건 |
| ERROR | 예상하지 못한 내부 처리, 서버 실행, 전송 또는 정리 실패 |

일반적인 400·401·403·404·405 등 기존 HTTP 오류 응답은 상태 코드만으로 WARNING·ERROR로 승격하지 않는다. 5xx 응답 객체를 반환한 사실도 Python 예외 발생과 같지 않다. 모든 응답은 전송 결과에 상태를 남기고, 실제 내부 예외는 별도 오류 정책에 따라 기록한다.

### 5.1. 풍부한 내부 진단과 레벨 선택 기준

사용자 요구에 따라 내부 로그는 오류 지점에만 추가하지 않는다. 정상 실행에서도 DEBUG를 활성화하면 등록부터 라우팅·검증·훅·핸들러·응답 제공·전송·정리까지 실제로 실행한 흐름을 재구성할 수 있어야 한다.

- 기존 로그의 이름만 변경하는 작업으로 끝내지 않는다. LOG-06부터 LOG-10까지의 관찰 지점별로 정상·실패·분기 경로의 기록 누락을 확인하고 보강한다.
- 주요 단계는 진입과 종료 결과가 대응되도록 기록한다. 실패한 단계는 성공 완료 대신 실패 단계와 예외 타입을 남긴다.
- 실행하지 않은 단계는 실행한 것처럼 기록하지 않는다. 미설정 훅·검증기를 매 요청마다 모두 나열하지 않되, OPTIONS 처리, 라우트·메서드 불일치, 반환 응답·직접 출력 선택 등 실행 경로를 바꾸는 분기는 DEBUG로 식별할 수 있어야 한다.
- 한 줄에 “요청 처리 중”만 남기지 않는다. 기존 요청 식별자, 처리 단계, 선택한 대상, 결과 등 해당 경계에서 확인 가능한 안전한 문맥을 함께 기록한다.
- 훅이 여러 개라면 종류·순번·구현 클래스로 어느 훅이 시작·완료·실패했는지 구별한다. 사용자 훅 내부 동작까지 자동 추적하거나 훅 계약을 변경하지 않는다.
- 소요 시간은 요청 실행·문서 생성·전송처럼 의미 있는 경계에 기록한다. 모든 함수에 타이머를 추가하거나 필드 변환마다 로그를 남기는 방식으로 양만 늘리지 않는다.
- DEBUG는 정상 요청의 상세 진단에 사용한다. INFO는 상세 단계 없이도 서버·Application의 상태 변화와 요청별 전송 결과를 파악할 수 있는 운영 요약으로 유지한다.
- WARNING은 처리를 계속하거나 연결을 정리할 수 있지만 주의가 필요한 비정상 사건에 사용한다. 일반적인 라우팅 실패·입력 검증 거부·정상 종료를 경고로 부풀리지 않는다.
- ERROR는 실제 내부 처리·전송·정리 실패에 사용한다. 사용자가 기본 INFO 수준으로 운영해도 장애가 DEBUG에만 묻히지 않도록 최종 오류 경계에서 기록한다.
- 수준 선택은 사용자 설정으로 정한 임계값에 맡기되, 사건 자체의 로그 레벨은 라이브러리 내부에서 일관되게 지정한다. 풍부한 로그를 출력하기 위해 라이브러리가 `setLevel(DEBUG)`를 호출해서는 안 된다.
- 동일 사건을 여러 레벨로 복제하지 않는다. DEBUG 단계 실패, ERROR 최종 예외, INFO 전송 결과는 각기 다른 정보를 제공할 때만 함께 남긴다.
- 상세 로그에도 LOG-13의 민감정보 제외와 LOG-14의 비용·동시성 기준을 동일하게 적용한다.

### LOG-06. Application과 서버 생명주기

- INFO: Application 시작 시도·완료, 종료 시작·완료. 완료는 해당 훅과 확장 처리를 실제로 마친 뒤에만 기록한다.
- DEBUG: 핸들러·확장 라우트 등록, 모듈 로드 요약, 확장 시작·정리 순서, 훅 호출 전후.
- ERROR: 시작 실패, 종료 중 각 독립적인 정리 실패. 시작 실패 후 정리 실패는 원래 시작 실패와 별도 사건으로 남긴다.
- INFO: 서버 실행 시도, 실제 수신 준비 완료, 종료 요청과 종료 결과. `adapter`, 호스트·포트를 포함한다.
- 바인딩 전의 설정 주소를 실제 수신 주소처럼 표현하지 않는다. 포트 `0`의 준비 완료 로그에는 확인된 실제 할당 포트를 사용한다.
- Gunicorn은 마스터 준비와 워커별 Application 시작·종료를 구분한다. 워커 로그는 표준 프로세스 문맥으로 구별할 수 있어야 한다.
- ERROR: 바인딩·서버 실행 실패. Application 생명주기에서 이미 기록한 예외를 서버가 같은 traceback으로 반복하지 않는다.
- 중복 종료 호출로 상태가 바뀌지 않았다면 새로운 “종료 완료”를 반복 기록하지 않는다.
- [시작 배너](../../../src/Startup.py)의 출력 내용·호출 계약과 색상 처리는 유지한다. 배너 출력만으로 서버 준비 완료를 판단하지 않는다.

### LOG-07. 요청 실행과 훅

- DEBUG: Application 요청 진입, 선택한 라우트 템플릿과 핸들러, Application 요청·응답·오류 훅의 호출·종료·실패 단계.
- DEBUG: RunRequest의 CORS 검사, 인증·파라미터·쿼리·헤더 검증, 본문 처리, 핸들러 인스턴스 생성, 요청 훅, `run()`, 응답 훅, CORS 응답 후처리.
- DEBUG: 확장 실행기의 확장 요청·응답·오류 훅과 실제 확장 호출.
- 단계 실패에는 단계명과 예외 타입을 남기되, 상위 서버로 전파되는 동일 예외의 traceback을 계층마다 반복하지 않는다.
- RequestRunner의 응답 훅은 반환 응답 경로와 직접 출력 경로에서 기존 호출 시점 그대로 관찰한다. 로깅을 위해 훅을 다시 실행하지 않는다.
- 실행 완료·응답 제공은 DEBUG로 기록한다. 이를 네트워크 전송 성공 또는 스트림 소비 완료라고 표현하지 않는다.
- Application·RunRequest를 서버 밖에서 직접 호출하는 경우에도 DEBUG 단계 로그와 기존 예외 전파를 제공한다. 최종 오류 기록은 호출자 책임이며, 이를 위해 추가 서버 경계를 만들지 않는다.

### LOG-08. HTTP 수신과 전송 결과

- 공통 요청 처리기가 요청 수신을 DEBUG로, 각 요청의 전송 결과 요약을 INFO로 한 번 기록한다. 내부 오류의 ERROR 로그와 결과 요약은 서로 다른 목적의 사건이다.
- 전송 결과에는 확인 가능한 요청 식별자, 메서드, 안전한 경로, 상태 코드, 결과, 전송 경계 소요 시간을 포함한다.
- 결과는 적어도 `completed`, `failed`, `disconnected`를 구분한다. 상태가 정해지지 않았다면 가짜 `200`이나 writer의 초기값 `500`으로 채우지 않는다.
- `completed`는 헤더 전송 시점이 아니라 writer 종료까지 성공한 경우에만 사용한다. 본문 소비·쓰기·flush·종료 중 실패했다면 앞서 200을 시작했어도 `failed`다.
- 응답 반환, 직접 출력, iterable 응답, chunked 출력, SSE, HEAD와 본문 없는 응답에 같은 결과 기준을 적용한다.
- 응답 전송 완료는 프레임워크가 전송 계층으로 전달을 마쳤다는 뜻이다. WSGI·ASGI 서버의 소켓 전송 완료나 클라이언트 수신까지 보장한 것처럼 기록하지 않는다.
- 전송 경계 시간은 공통 처리 진입부터 writer 종료 또는 실패까지다. RunRequest 실행 시간, 후속 자원 정리 시간과 혼합하지 않으며 단조 시계를 사용한다.
- 최종 본문 정리 실패는 별도 ERROR다. 이미 완료한 전송을 미전송으로 바꾸지 않고, 정리까지 성공한 것처럼 표현하지 않는다.
- 응답 크기는 이번 필수 항목이 아니다. 나중에 기록한다면 Content-Length를 실제 송신량으로 오인하거나 측정하려고 iterable을 미리 소비해서는 안 된다.
- Python 기본 접근 로그와 새 공통 결과 로그가 같은 요청을 중복 요약하지 않도록 한다. 공통 처리 진입 전 HTTP 파싱 거부는 어댑터가 안전한 상태·사유 코드로 기록한다.
- Gunicorn·Uvicorn 자체 접근 로그는 별도 출처다. 라이브러리가 강제로 끄지 않고, 중복 출력을 원치 않는 사용자가 외부 접근 로그를 비활성화하는 기존 옵션을 문서화한다.

### LOG-09. 내장 확장

| 확장 | 필요한 진단 | 주의사항 |
| --- | --- | --- |

| Ping | DEBUG: 판정한 Application 실행 상태 | 정상 시작·종료 상태의 503을 매번 WARNING으로 기록하지 않는다. 새로운 probe나 상태 변화 추적기를 추가하지 않는다. |

| Status | DEBUG: 상태 페이지 생성 요약 | Metrics URI를 사용하는 현재 계약을 유지한다. 외부 지표 조회나 연결 확인 기능을 추가하지 않는다. |
| Specifications | DEBUG: 문서 생성 시작·완료, 라우트 수와 소요 시간 | 전체 스키마·예제·인증 설정을 덤프하지 않는다. |
| Swagger | DEBUG: 문서 UI 응답 생성 요약 | 외부 문서·스크립트 응답을 새로 수집하거나 출력하지 않는다. |

공통 확장 등록·시작·종료는 Application이 기록한다. 각 확장은 고유 처리만 추가하고 공통 HTTP 접근 기록을 반복하지 않는다. 상위로 전파되는 확장 요청 실패의 최종 ERROR·traceback은 서버 경계가 담당한다.

### LOG-10. 스트리밍과 WebSocket

- 스트림 시작·종료·실패를 관찰하되 chunk, SSE 이벤트, WebSocket frame마다 로그를 추가하지 않는다.
- WebSocket 업그레이드 성공과 정상 종료는 DEBUG, 프로토콜 위반은 WARNING으로 기록한다. 연결 식별에는 기존 요청 식별자를 사용한다.
- 101 상태와 업그레이드 성공을 WebSocket 세션 전체 성공으로 표현하지 않는다. 세션 종료·실패는 구분하여 남긴다.
- WebSocket 경로에서도 공통 서버 처리기의 결과 요약은 한 번만 기록한다. Uvicorn 연결 보조 계층은 이미 기록된 요청 예외를 다시 ERROR로 기록하지 않는다.
- 정상 close와 서버 종료에 따른 취소는 내부 장애로 승격하지 않는다. 예상하지 못한 연결 단절은 서버 경계에서 WARNING으로 기록한다.
- close code와 프레임워크가 정의한 안전한 사유 코드는 기록할 수 있지만, 상대가 보낸 close reason·메시지·ping payload는 기록하지 않는다.
- 프로토콜 위반을 경고로 기록한 뒤 오류 close 전송도 실패했다면 서로 다른 사건으로 구분한다.
- Gunicorn·WSGI의 업그레이드 미지원 계약을 유지하며, 로깅을 위해 우회 지원하지 않는다.

## 6. 오류 기록과 기존 동작 보존

### LOG-11. 최종 오류의 기록 책임

| 사건 | 최종 기록 위치·수준 |
| --- | --- |
| 요청 실행 중 예상하지 못한 예외, 응답 시작 전 | 공통 요청 처리기 ERROR + traceback. 기존대로 500 응답을 시도 |
| 응답 시작 이후 실행·본문 소비·전송 실패 | 공통 요청 처리기 ERROR + traceback. 두 번째 오류 응답을 보내지 않음 |
| 요청·전송 중 연결 단절 | 공통 요청 처리기 WARNING. 내부 오류와 같은 사건으로 중복 ERROR 기록하지 않음 |
| 공통 처리기에 도달하지 못한 어댑터 내부 실패 | 해당 어댑터의 `DefEssential.Server` ERROR + traceback |
| Application 시작·종료 실패 | Application ERROR + traceback. 확장 내부의 동일 전파 예외와 중복하지 않음 |
| 처리 실패 중 추가 자원 정리 실패 | 원래 실패를 보존하는 정리 지점에서 별도의 ERROR + traceback |
| 직접 호출한 Application·RunRequest의 전파 예외 | DEBUG 단계 관찰 후 기존대로 전파. 최종 ERROR는 외부 호출자 책임 |

- 같은 예외가 확장 → RunRequest → Application → 서버로 전파되었다고 매번 ERROR·traceback을 남기지 않는다. 새 예외를 던진 오류 훅은 실패 단계와 예외 연결 관계로 구분한다.
- 중복 제거를 위해 예외 객체에 임의 속성을 붙이거나 전역 예외 캐시를 추가하지 않는다. 기록 경계를 배치하여 해결한다.
- 로깅을 위해 예외를 삼키거나 `None`, 더미 응답, 성공 상태로 대체하지 않는다. 기존의 예외 전파, 정리 순서, 첫 정리 오류 보존 계약을 유지한다.
- `KeyboardInterrupt`·`SystemExit` 등 BaseException 전체를 일반 요청 오류로 포착하지 않는다. 기존 종료 제어 흐름을 유지한다.
- 사용자 훅이 자체 기록한 로그나 외부 서버의 독립 오류 로그까지 중복 제거한다고 보장하지 않는다.

## 7. 문맥·민감정보·비용

### LOG-12. 로그 문맥

- 일반 포매터의 `%(name)s`, `%(levelname)s`, `%(message)s`만으로도 사건을 이해할 수 있게 한다. 사용자 정의 필드가 반드시 필요한 포매터를 강요하지 않는다.
- 요청 생성 후에는 기존 `Request.id`를 사용한다. 기존 식별자를 외부 헤더 값으로 교체하거나 새 추적 ID를 도입하지 않는다.
- Request 생성 전 파싱 실패처럼 없는 문맥은 생략한다. 존재하지 않는 요청 ID·상태·소요 시간을 정상 값으로 만들어 넣지 않는다.
- 요청 훅이 다른 Request를 반환할 수 있다는 기존 계약을 보존한다. 교체 전후 경계에서 관찰한 식별자를 구분하고, 한 서버 요청의 수신·결과 대응에는 최초 생성한 Request의 ID를 유지한다.
- 훅이 Request를 교체하면 DEBUG로 이전·새 ID의 대응을 남기되, 요청 객체를 변경하거나 새 공개 Context 인자를 추가하지 않는다.
- 단계 로그에는 단계명, 대상 핸들러·확장·훅의 정규 클래스명, 결과를 포함한다. 반복 훅은 종류와 순번으로 구분한다.
- 서버 로그에는 어댑터 이름을 포함하고, 다중 워커 구분은 표준 `process`·`processName`과 `threadName`을 사용자가 포매터에 넣을 수 있게 안내한다.
- 새 구조화 로그 스키마나 로그 문구 전체를 공개 API로 확정하지 않는다. 테스트는 필요한 문맥과 의미를 검증한다.

### LOG-13. 민감정보와 외부 입력

- DEBUG를 포함하여 요청·응답 본문, 인증 헤더, Cookie·Set-Cookie, 세션, 토큰, 비밀번호, 검증 대상 값, 파일 내용은 기록하지 않는다.
- 원시 URI·query string, 파라미터·헤더 전체, Request·Response·사용자 객체의 `repr()`를 출력하지 않는다.
- 라우팅 이후에는 등록된 라우트 템플릿을 우선 사용한다. 매칭 전 경로가 필요하면 query를 제거하고 제어 문자를 이스케이프하며, 한 경로 표현을 최대 256자로 제한한다.
- query 제거·길이 제한은 경로 안의 비밀 값을 자동 제거하지 않는다. 매칭 전 경로를 기록할 때의 한계와 URL 경로에 비밀 값을 넣지 말아야 함을 사용 안내에 명시한다.
- 사용자 입력을 포맷 문자열로 사용하지 않는다. 지연 포맷팅 인자로 전달하며, 한 사건이 개행·제어 문자로 다른 로그처럼 보이지 않게 한다.
- 오류의 일반 문맥에는 예외 타입과 안전한 단계·사유 코드를 사용하고 `str(error)`를 무조건 덧붙이지 않는다.
- 내부 오류 traceback에는 예외 메시지·연결된 예외·소스 줄이 포함될 수 있다. 이를 완전한 비밀정보 차단으로 설명하지 않으며, 사용자 예외 메시지의 민감정보 금지와 애플리케이션 측 필터링 책임을 문서화한다.
- traceback 진단을 제거하거나 숨기기 위한 임의의 광범위 마스킹 시스템은 이번 범위에 추가하지 않는다.

### LOG-14. 비용과 동시성

- DEBUG 비활성 시 로그만을 위한 문서 생성, 집계 스냅샷, 객체 직렬화, 본문 읽기를 하지 않는다. 필요한 고비용 문맥은 레벨 확인 후 계산한다.
- 크기·시간 측정을 위해 스트림을 버퍼링·재소비하거나 요청·응답 전달 순서를 바꾸지 않는다.
- 병렬 요청의 ID·단계·타이머를 클래스나 모듈의 공유 가변 상태에 저장하지 않는다.
- 새 잠금·백그라운드 스레드·파일 I/O를 로깅 목적으로 추가하지 않는다.
- 라이브러리가 로깅 실패를 숨기는 광범위 예외 처리나 대체 출력 경로를 추가하지 않는다.

## 8. 사용자 안내와 샘플

### LOG-15. 설정 예제와 문서

구현 시 [사용 안내](../../../README.md)에 로거 목록, 레벨, 기록 책임, 미설정 동작, 민감정보 한계와 다음 형태의 설정 예제를 추가한다. [샘플](../../../samples/Sample.py)은 `ApplicationStartup` 구현을 `on_startup`의 첫 번째 훅으로 등록하여 출력 설정을 수행한다. import 시점이나 실행 진입점의 `basicConfig()`로 설정하지 않는다.

```python
from logging import DEBUG, Filter, Formatter, StreamHandler, getLogger

from DefEssential import Application, ApplicationStartup


class LoggingSetup(ApplicationStartup):
  def __init__(self) -> None:
    sources = (Filter('Sample'), Filter('DefEssential'))
    self.handler = StreamHandler()
    self.handler.setFormatter(Formatter(
      '%(asctime)s %(processName)s %(name)s %(levelname)s %(message)s'
    ))
    self.handler.addFilter(
      lambda record: any(source.filter(record) for source in sources)
    )

  def __call__(self) -> None:
    root = getLogger()
    root.setLevel(DEBUG)
    if self.handler not in root.handlers:
      root.addHandler(self.handler)


app = Application(on_startup=LoggingSetup())
```

- 필터는 루트 로거가 아니라 핸들러에 적용한다. `Sample`·`Sample.*`와 `DefEssential`·`DefEssential.*`만 선택하고 `SampleExtra`, `DefEssentialExtra`, 외부 라이브러리 로거는 제외한다.
- 기본 포맷은 DefStream과 같은 `%(asctime)s %(processName)s %(name)s %(levelname)s %(message)s`로 한다. 스레드 구분이 필요하면 사용자가 `%(threadName)s`를 추가할 수 있다.
- 위 예제는 독립 실행 애플리케이션용이다. 기존 핸들러를 강제로 제거하거나 `force=True`로 덮어쓰지 않는다. 출처 제한은 샘플이 추가한 핸들러에 대한 보장이며, 다른 기존 핸들러의 출력까지 차단하지 않는다.
- 동일 Application의 중지 후 재시작에도 같은 설정 훅이 핸들러를 중복 등록하지 않아야 한다. 기존 시작 관찰 훅 등 다른 시작 훅은 출력 설정 훅 뒤에 실행한다.
- 시작 훅 이전의 Application 구성·라우트 등록·시작 시도 로그는 이 설정으로 소급 출력할 수 없다. 해당 로그 수집을 위해 라이브러리의 시작 순서를 바꾸거나 버퍼를 추가하지 않는다. 시작 배너는 기존처럼 로깅과 별도로 출력된다.
- 샘플에는 `DefStream` 등 다른 출처를 추가하지 않는다. 두 프레임워크를 함께 수집하는 별도 사용자 설정과 구분한다.
- [샘플](../../../samples/Sample.py)은 `Sample`을 유지하되 출처 제한 설정을 사용하고 원시 URI·예외 메시지를 무조건 출력하지 않는다.
- 샘플의 훅 관찰 로그는 DEBUG로 두고 “훅 완료”로 표현하여 서버의 INFO 전송 결과와 의미·빈도가 겹치지 않게 한다.
- 새 필수 설치 의존성을 추가하지 않는다. Gunicorn 워커의 로깅은 기존 사용자 설정·서버 훅으로 구성하는 방법을 안내하고 부모 핸들러의 자동 전달을 보장하지 않는다.
- Uvicorn 자체 로그 설정을 보존하려면 기존 `log_config` 옵션을 어떻게 사용하는지, 외부 접근 로그 중복은 기존 `access_log`·`accesslog` 옵션으로 어떻게 제어하는지 어댑터별로 안내한다.

## 9. 수용 기준과 검증

구현 완료는 아래 항목을 테스트와 실제 실행 가능한 샘플로 확인한 상태를 뜻한다. 현재 문서 작성만으로 통과했다고 간주하지 않는다.

검증은 [기존 테스트](../../../tests)의 실행 방식과 테스트 더블을 재사용한다. 요청·훅·writer·전송 적합성 테스트를 우선 실행하고 관련 회귀 테스트로 확대한다. Gunicorn 실제 실행은 POSIX/Linux 또는 WSL에서 확인하며, Windows의 미지원 또는 선택 의존성 부재를 성공으로 처리하지 않고 검증 제약으로 기록한다.
