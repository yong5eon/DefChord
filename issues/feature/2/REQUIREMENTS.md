# 생명 주기 훅 공통 요구사항 명세서

## 1. 목적과 문서의 역할

이 문서는 [생명 주기 훅 추가 및 변경 이슈](./ISSUE.md)의 상위 명세서이다. 사전 소스 조사 결과, 세 구성요소에 공통으로 적용할 요구사항, 사용자와 확정한 설계 방향을 기록한다.

`Application`, `Extension`, `RequestRunner` 훅은 각각 별도의 하위 이슈에서 요구사항 수립, 상세 명세 작성, 구현 및 검증을 진행한다. 이 문서는 개별 훅의 이름·시그니처·호출 순서를 확정하는 상세 API 명세를 대신하지 않는다.

## 2. 배경

현재 소스에 생명 주기와 확장점이 전혀 없는 것은 아니다. 애플리케이션 시작·종료, 확장의 바인딩 및 요청 관찰, 요청 핸들러의 요청·응답 필터가 이미 존재한다. 해결할 문제는 이러한 구조를 바탕으로 사용자가 필요한 시점에 동작을 연결할 수 있는 훅 계약을 정립하는 것이다.

사용자가 설명한 설계 배경에 따르면 기존 `RequestFilter`와 `ResponseFilter`는 AWS FaaS에서 `RequestRunner`만 Lambda 형태로 서비스하는 사용 사례를 고려해 도입되었다. 이 배경을 모든 구성요소의 일반 생명 주기 훅 계약으로 그대로 적용할 필요는 없다.

따라서 기존 필터의 이름이나 인터페이스를 출발점으로 일괄 확장하지 않고, 구성요소별 실제 수명과 책임을 확인한 뒤 필요한 훅을 정의한다.

## 3. 사전 조사 결과

이 절은 현재 구현에 대한 조사 기록이며, 변경 후 API 계약을 의미하지 않는다.

### 3.1 Application

- 생성 시 라우터와 확장 등록 상태를 구성하고, 확장 라우트를 등록한 뒤 확장을 바인딩한다. 확장은 하나의 Application에 소속된다.
- `start()`는 확장을 등록 순서대로 시작하고, 실패하면 시작에 성공한 확장을 역순으로 정리한다.
- `stop()`은 확장을 역순으로 종료한다. 종료 오류를 기록하면서 나머지 확장도 정리하고, 첫 오류를 전파한다.
- 이미 실행 중인 상태의 시작은 오류이며, 실행 중이 아닐 때의 종료는 아무 작업도 하지 않는다.
- 요청 호출 시 라우팅과 요청 조건을 확인하고 요청 실행기로 위임한다. 직접 호출은 `running` 상태를 검사하지 않는다.
- Python 및 Uvicorn 서버는 서버 실행 경로에서, Gunicorn은 워커 초기화·종료 경로에서 애플리케이션을 시작·종료한다.
- 사용자가 생성자에서 별도로 입력하는 생명 주기 훅 계약은 현재 없다.

근거: [Application](../../../src/Application.py), [Python 서버](../../../src/Adapter/Implements/Python/Server.py), [Uvicorn 서버](../../../src/Adapter/Implements/Uvicorn/Server.py), [Gunicorn 서버](../../../src/Adapter/Implements/Gunicorn/Server.py).

### 3.2 Extension

- 생성된 확장은 Application 구성 과정에서 바인딩되고, 애플리케이션 시작·종료 및 요청 관찰에 참여한다.
- 기존 확장점으로 `bind`, `start`, `stop`, `begin`, `end`가 있다.
- 공통 서버 요청 처리기는 요청 생성 후 확장의 `begin(request)`를 등록 순서대로 호출한다. 성공한 호출의 반환값은 요청별 관찰 컨텍스트로 보관한다.
- 요청 정리 시 `end(request, context, status, error)`를 역순으로 호출한다. 요청 생성 실패 시에는 요청 관찰이 시작되지 않으며, `begin` 실패 시에는 이미 성공한 확장만 정리 대상이다.
- `end`의 예외는 기록하되 전파하지 않는다. 현재 `end`는 응답을 대체하는 오류 처리보다는 정리·관찰 목적의 확장점이다.
- 확장 HTTP 라우트는 내부 RequestRunner 클래스로 연결된다. 따라서 두 구성요소의 훅이 함께 실행될 수 있는 경로가 존재한다.

근거: [Extension](../../../src/Extension.py), [공통 요청 처리기](../../../src/Adapter/RequestHandler.py), [확장 요청 실행 클래스 생성](../../../src/Runners/RunExtension.py).

### 3.3 RequestRunner

- 클래스 선언 시 설정이 구성되고, Application에는 핸들러 클래스가 등록된다.
- 요청 실행기는 CORS 원본 확인, 인증·파라미터·쿼리·헤더 검증, 본문 처리를 수행한 뒤 핸들러 인스턴스를 생성한다.
- 인스턴스 생성 후 요청 필터, `run()`, 응답 필터 순서로 진행한다. 요청 필터의 조기 응답은 `run()`과 응답 필터 경로를 생략한다.
- 공개 설정명은 현재 `onRequest`, `onResponse`이며 내부 속성명은 `on_request`, `on_response`이다.
- 필터는 단일 객체 또는 복수 객체를 받으며, 요청·응답을 변경할 수 있다.
- `run()`은 Response를 반환하거나 writer로 직접 출력한다. 직접 출력의 응답 필터는 writer 콜백에 연결된다.
- 인스턴스 생성 전 검증 실패와 라우팅 실패 등은 핸들러 인스턴스의 실행 범위 밖에 있다. 통합 오류 훅은 없으며 일반적인 HTTP 오류 응답 처리는 공통 서버 요청 처리기가 담당한다.

근거: [RequestRunner](../../../src/RequestRunner.py), [요청 실행기](../../../src/Runners/RunRequest.py), [공통 요청 처리기](../../../src/Adapter/RequestHandler.py).

### 3.4 계층 간 설계에 영향을 주는 사실

- 애플리케이션 생성, 서버·워커 실행, 개별 요청 처리는 서로 다른 수명이다.
- `Application(request)` 직접 호출과 서버 공통 요청 처리기 경로는 동일하지 않다. 기존 확장 요청 관찰은 후자에 연결되어 있다.
- 응답 생성 완료와 응답 전송 완료는 다른 시점이다. 스트리밍·직접 출력에서는 일부 응답이 이미 전송된 뒤에도 실패할 수 있다.
- 공통 요청 처리기는 응답이 시작되기 전 오류를 HTTP 응답으로 변환할 수 있지만, 전송이 시작된 뒤에는 새 오류 응답을 보내지 않고 실패를 전파한다.
- 기존 필터, 확장 관찰 메서드 및 새 훅을 연결할 때 중복 실행과 책임 중첩을 확인해야 한다.

## 4. 공통 확정 사항

### C-1. 작업 분리

- Application 훅, Extension 훅, RequestRunner 훅은 각각의 하위 이슈에서 진행한다.
- 각 하위 이슈에서 구체 요구사항을 다시 수립하고 상세 명세, 구현 및 테스트를 완결한다.
- 상위 이슈는 공통 기준과 하위 작업 간 일관성을 관리한다.

### C-2. 훅 계약의 입력 지점

| 구성요소 | 확정한 훅 계약 방식 |
| --- | --- |
| Application | 생성자에서 훅을 입력받는다. |
| Extension | `__init_subclass__`를 통해 클래스 선언 시 훅을 계약한다. |
| RequestRunner | `__init_subclass__`를 통해 클래스 선언 시 훅을 계약한다. |

### C-3. 복수 훅 지원

- 세 구성요소 모두 단일 훅뿐 아니라 복수 훅을 연결해 사용할 수 있어야 한다.
- 단일·복수 입력의 구체적인 타입과 인자 형태는 상세 명세에서 정한다.
- 복수 훅을 지원한다는 결정이 모든 이벤트에 동일한 실행 순서나 오류 정책을 적용한다는 뜻은 아니다.

### C-4. 기존 필터 설계에 대한 비종속

- 기존 `RequestFilter`·`ResponseFilter` 계약을 새 생명 주기 훅의 필수 형태로 강제하지 않는다.
- 필터와 생명 주기 훅의 유지·통합·분리 여부는 역할과 기존 사용 코드의 영향을 확인해 결정한다.

### C-5. 구성요소 경계 안에서만 훅 실행

- Application, Extension, RequestRunner의 책임과 생명 주기 경계를 구분하고, 훅은 소속 구성요소의 경계 안에서만 동작해야 한다.
- 상위 구성요소가 다른 구성요소의 실행을 위임·관리하더라도, 그 사실만으로 다른 구성요소의 내부 이벤트까지 자신의 훅 대상으로 삼지 않는다.
- 오류가 호출자에게 전파되는 것과, 호출자가 하위 구성요소 내부의 오류 이벤트를 직접 구독하는 것은 구분한다. 전파된 오류를 다루는 경우에도 자신의 실행 경계에서 발생한 실패로 처리한다.
- 각 하위 이슈는 개별 훅을 선정하기 전에 담당 경계를 명세해야 한다. 경계가 겹치거나 비어 있는 부분은 관련 하위 이슈와 조정하고 상위 명세에 반영한다.

## 5. 공통 요구사항

### CR-1. 책임과 실행 경계

- 각 훅은 해결할 사용 사례, 대상 구성요소, 실행 시점과 수명을 명시해야 한다.
- 동일 요청에서 여러 계층의 훅이 실행되는 경우 역할과 상대적인 호출 관계를 명시해야 한다.
- 프로세스·워커별 실행과 요청별 실행을 구분하고, 직접 호출과 서버 경로의 적용 범위를 명시해야 한다.
- 각 하위 명세는 경계의 시작·종료 조건, 소유하는 상태·자원, 외부로 위임하는 처리와 제외 대상을 정의해야 한다.
- 훅 호출 여부는 단순히 같은 요청이나 호출 스택에 속하는지가 아니라 해당 구성요소의 실행 경계에 진입했는지로 판단해야 한다.

| 구성요소 | 경계를 정의할 책임 영역 | 경계 구분 시 주의점 |
| --- | --- | --- |
| Application | 자신의 구성·실행 상태와 요청 디스패치 | 개별 Extension·RequestRunner의 내부 실행 및 서버의 전송 생명 주기와 구분한다. 요청 디스패치 완료를 실제 응답 전송 완료와 동일시하지 않는다. |
| Extension | 해당 확장 자신의 바인딩·시작·종료와 요청 관찰 참여 | 관찰하는 전체 요청의 수명과 확장 자신의 참여 수명을 구분한다. 다른 확장이나 내부 연결용 RequestRunner의 이벤트를 자동으로 자신의 이벤트로 취급하지 않는다. |
| RequestRunner | 해당 핸들러에 대한 요청 실행과 그에 속하는 처리 | 클래스 설정·인스턴스 수명·실행 파이프라인을 구분한다. 검증·본문 처리의 소속은 상세 명세에서 정하며, 핸들러에 도달하지 않은 요청이나 외부 전송 처리를 암묵적으로 포함하지 않는다. |

다음 경계 정의를 각 하위 이슈의 공통 기준으로 적용한다. 개별 훅 이름·시그니처와 정확한 호출 위치는 이 경계를 지키도록 각 하위 이슈에서 명세한다.

#### Application의 경계와 훅 역할

Application은 애플리케이션의 구성과 실행 상태를 관리하고, 준비된 요청의 처리 대상을 결정해 실행을 위임하며, 그 결과를 호출자에게 돌려준다.

- **구성·실행 경계:** 자신의 생성·구성, 라우트·확장 등록 상태 및 시작·종료 상태를 관리한다. 소속 확장의 시작·종료를 조정하지만 확장 내부 자원 초기화·정리까지 직접 소유하지 않는다.
- **요청 경계 시작:** 서버 또는 직접 호출자가 준비한 Request를 입력받아 디스패치를 시작하는 시점이다.
- **요청 경계 안의 처리:** 경로·메서드 선택, 디스패치에 필요한 조건 확인, 처리 대상에 실행 위임, 결과 또는 오류의 반환이다.
- **요청 경계 종료:** 위임한 실행의 반환 결과 또는 전파된 오류를 Application 호출자에게 전달하는 시점이다.
- **훅 역할:** Application 자신의 구성·시작·종료 및 디스패치 진입·완료·실패에 사용자 동작을 연결한다. 위임한 처리의 실패는 Application 디스패치 실패로 다룰 수 있으나, 하위 처리의 내부 이벤트를 직접 구독하는 것으로 정의하지 않는다.
- **제외:** 소켓·연결 관리, HTTP 요청 행·헤더의 수신·파싱, 핸들러별 인증·입력 검증·본문 해석, 개별 확장·핸들러의 내부 단계, 실제 응답 전송 완료와 연결 종료.

헤더 수신·파싱은 Application 진입 전에 수행된다. Application이 읽힌 헤더를 디스패치 판단에 참조하는 것과 헤더를 수신·파싱하는 것은 다른 책임이다. 현재 Application의 본문 관련 사전 검사 중 무엇을 유지할지는 이 기준에 따라 하위 이슈에서 명세한다.

#### Extension의 경계와 훅 역할

Extension은 Application에 소속된 개별 확장 기능이며, 자신의 자원 수명과 명시적으로 참여한 요청 관찰·처리를 책임진다.

- **바인딩·실행 경계:** 자신의 Application 바인딩, 시작·종료와 자신이 소유한 자원의 초기화·정리를 대상으로 한다. Application 전체나 다른 확장의 수명을 소유하지 않는다.
- **요청 관찰 경계 시작:** 해당 확장이 요청 관찰에 참여하는 시점이다. Application이나 다른 확장의 요청 처리 시작과 자동으로 동일시하지 않는다.
- **요청 관찰 경계 종료:** 참여한 관찰의 결과를 기록하고 자신의 요청별 컨텍스트·자원을 정리하는 시점이다. 기존 `begin/end`의 성공한 참여만 역순 정리하는 계약과의 관계를 상세 명세에 명시한다.
- **확장 HTTP 처리 경계:** 자신의 라우트로 위임된 확장 기능을 처리한다. 이 경계와 전체 요청 관찰 경계는 별개의 참여이며, 같은 확장에 속해도 서로의 훅을 자동으로 대신 호출하지 않는다.
- **훅 역할:** 해당 확장 자신의 바인딩·시작·종료, 요청 관찰 참여·정리 및 확장 기능 실행에 필요한 동작을 연결한다. 이 중 어떤 이벤트를 공개 훅으로 제공할지는 하위 이슈에서 선정한다.
- **제외:** 전역 라우팅과 Application 실행 상태 관리, 다른 확장의 내부 동작, 일반 핸들러의 내부 검증·실행 단계, 연결·응답 전송 자체의 제어.

기존 `end`처럼 서버가 전달한 상태·오류를 관찰하는 것은 허용된다. 전송 결과를 관찰한다고 해서 전송 단계를 소유하거나 전송 훅을 제공하는 것은 아니다. 내부 연결용 RequestRunner를 거치는 경로에서는 확장 훅과 실행기 훅의 적용 대상을 명시해 의도하지 않은 이중 실행을 방지한다.

#### RequestRunner의 경계와 훅 역할

RequestRunner는 선택된 핸들러의 요청별 실행을 책임진다. 클래스 선언의 설정 수명, 핸들러 인스턴스 수명, 해당 핸들러의 요청 실행 파이프라인을 구분한다.

- **선언 경계:** `__init_subclass__`에서 해당 핸들러 클래스의 훅 계약을 구성한다. 계약 등록 자체가 요청 실행 이벤트를 발생시키지는 않는다.
- **요청 실행 경계 시작:** 디스패치에서 선택된 핸들러의 요청 실행 파이프라인에 진입하는 시점이다. 현재 인스턴스 생성 전 검증·본문 처리는 이 파이프라인에 있으므로 인스턴스 생성만을 전체 요청 실행의 시작으로 간주하지 않는다.
- **경계 안의 처리:** 해당 핸들러에 설정된 검증·본문 처리·필터·`run()` 및 응답 후처리 중 명세에서 훅 대상으로 정한 단계이다. 어느 단계까지 각 훅이 관찰·개입하는지는 하위 명세에서 구분한다.
- **요청 실행 경계 종료:** 실행 결과를 디스패치 호출자에게 반환하거나 실행 오류를 전파하는 시점이다. 직접 출력은 writer 계약에 따른 실행 완료를 포함하지만 연결 수명 전체를 포함하지 않는다.
- **훅 역할:** 해당 핸들러의 실행 전·정상 완료·실패 및 명시된 요청·응답 처리 단계에 동작을 연결한다. 인스턴스 메서드 주변의 훅과 검증을 포함한 파이프라인 훅을 혼동하지 않도록 적용 범위를 명세한다.
- **제외:** Application 구성·시작·종료, 라우트 선택 및 선택 전 실패, 다른 핸들러나 확장의 실행, 반환 이후 외부에서 수행하는 응답 전송·스트림 소비 및 연결 종료.

#### 경계 사이의 결과와 오류 전달

- 라우트가 선택되지 않은 요청은 Application 디스패치에서 실패할 수 있지만, 선택되지 않은 RequestRunner의 실행 훅을 호출해서는 안 된다.
- 선택한 핸들러의 검증 실패는 해당 요청 실행 파이프라인의 실패일 수 있으나, 아직 실행하지 않은 `run()`의 정상 완료로 취급해서는 안 된다.
- 하위 오류가 상위로 전파되면 각 경계는 자신의 실패로 관찰할 수 있다. 이는 동일 훅의 중복 호출이 아니라 서로 다른 대상의 결과 관찰이며, 호출·전파 순서는 상세 명세에서 정한다.
- 핸들러 반환 후 서버가 응답 스트림을 소비하다 실패하면 이미 종료한 RequestRunner 실행 훅을 다시 호출하지 않는다. 참여 중인 Extension은 자신의 관찰 계약에 따라 서버가 전달한 실패를 관찰할 수 있다.
- 정상 반환, 조기 응답, 직접 출력 중 어느 경우에도 Application 디스패치 완료와 RequestRunner 실행 완료를 클라이언트의 응답 수신 완료로 표현하지 않는다.

### CR-2. 명시적인 계약과 검증

- 입력 및 반환 타입, 유효성 검사 시점, 훅 미설정 시 동작을 정의해야 한다.
- 잘못된 훅 입력을 조용히 무시하거나 다른 값으로 대체하지 않아야 한다.
- 단일·복수 훅이 동일한 의미의 계약을 따르도록 하고, 호출 순서와 중간 실패 시 나머지 훅의 실행 여부를 명시해야 한다.
- 훅 객체나 요청별 상태가 여러 클래스·Application·동시 요청 사이에서 어떻게 공유되는지 명확히 해야 한다.

### CR-3. 오류와 자원 정리

- 정상 완료, 중간 실패, 조기 응답 및 정리 경로에서의 훅 호출 여부를 정의해야 한다.
- 원래 처리 오류와 훅·정리 오류가 함께 발생했을 때 기록·전파할 오류와 남은 정리 작업의 처리 방식을 명시해야 한다.
- 응답 전송 시작 이후에는 새 응답을 보내는 방식으로 실패를 숨기지 않아야 한다.
- 오류 관찰, 예외 변환, 응답 대체 및 자원 정리는 서로 다른 책임으로 구분해야 한다.

### CR-4. 기존 동작 및 호환성

- 훅을 설정하지 않은 경우 기존 동작을 유지하는 것을 기본으로 한다.
- 기존 메서드·필터와의 관계 및 공개 API 변경 영향을 조사하고, 의도적인 변경은 하위 명세에 명시해야 한다.
- 기존 필터명 변경과 호환 별칭 제공 여부는 이 상위 명세에서 확정하지 않는다.

### CR-5. 검증과 문서화

- 각 하위 이슈는 결정한 계약에 대한 정상·실패·복수 훅 테스트를 포함해야 한다.
- 해당 구성요소와 관련된 기존 테스트로 회귀 여부를 확인해야 한다.
- 계층 간 훅이 결합되는 경로는 관련 하위 이슈의 명세에서 책임을 연결하고 통합 검증해야 한다.
- 경계 안의 훅 호출뿐 아니라 경계에 진입하지 않은 경우와 경계 종료 이후의 비호출도 검증해야 한다. 다른 인스턴스·클래스·확장의 실행이 잘못된 대상의 훅을 호출하지 않는지 확인해야 한다.
- 공개 API와 예제를 구현된 계약에 맞춰 문서화해야 한다.

## 6. 하위 이슈의 범위와 인계 사항

아래 항목은 앞서 확인한 필요 시점과 후속 조사 대상을 인계하기 위한 것이다. 확정된 개별 훅 목록이나 API를 뜻하지 않는다. 하위 이슈 식별자는 사용자가 확인한 매핑이며, 로컬 문서가 아직 없어 링크는 추가하지 않는다.

| 하위 이슈 식별자 | 대상 | 인계할 필요 시점·기능 | 해당 이슈에서 수립할 상세 명세 |
| --- | --- | --- | --- |
| `feature/4` | Application 훅 | 생성·구성, 시작, 요청 디스패치 진입·완료, 종료 | 생성자 계약, 개별 이벤트와 시그니처, 생성·서버·워커 수명, 확장과의 호출 관계 |
| `feature/5` | Extension 훅 | 기존 앱 시작·종료 및 요청 관찰 확장점의 유지·활용 | 클래스 선언 계약, 기존 `bind/start/stop/begin/end`와의 관계, 내부 RequestRunner와의 책임 구분 |
| `feature/6` | RequestRunner 훅 | 실행 직전, 정상 완료, 오류 시, 요청·응답 필터 기능 | 클래스 선언 계약, 검증·본문 처리의 포함 범위, 필터와 새 훅의 관계, 조기 응답·직접 출력·스트리밍의 처리 경계 |

모든 하위 이슈는 먼저 담당 경계와 제외 대상을 정의한 뒤 훅 이름, 시그니처, 복수 입력 형식, 실행 순서, 실패 정책, 상속 시 계약, 호환성 및 수용 기준을 각각 명세해야 한다. 앞서 인계한 필요 시점·기능이 담당 경계 밖이라면 그대로 구현하지 않고 적절한 구성요소로 조정해야 한다. 계층 간 공통 결정에 영향을 주는 변경은 상위 명세에도 반영한다.

## 7. 상위 이슈 완료 기준

- 사전 조사 결과와 공통 확정 사항이 각 하위 명세에 인계되어 있다.
- 세 하위 이슈의 요구사항·상세 명세·구현·검증이 완료되어 있다.
- 생성자 또는 클래스 선언을 통한 계약과 단일·복수 훅 지원이 각 구성요소에서 검증되어 있다.
- 계층 간 호출 관계, 오류 처리 및 기존 동작과의 호환성에 상충하는 계약이 없다.
- 구성요소별 책임·생명 주기 경계가 명세되어 있고, 훅이 해당 경계 안에서만 실행됨을 검증했다.
- 결합 경로의 통합 검증 결과와 의도적인 동작 변경이 관련 문서에 기록되어 있다.
