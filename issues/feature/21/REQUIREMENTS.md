# 오류 응답 처리 요구사항 명세서

## 목적

요청 처리 중 예외가 발생했을 때 `RequestRunner`, `Extension`, `Application`의 기존 오류 훅에서 `Response`를 반환하여 해당 예외를 HTTP 응답으로 처리할 수 있게 한다. 오류 훅이 `None`을 반환하면 기존처럼 오류를 관찰한 뒤 상위 계층과 HTTP adapter로 전파한다.

## 배경과 현재 동작

- 세 계층에는 각각 `RequestRunnerRequestError`, `ExtensionRequestError`, `ApplicationRequestError` 오류 훅이 이미 있다.
- 현재 오류 훅은 `(request, error)`를 받고 `None`을 반환해야 한다. 훅 실행 뒤 예외는 다시 발생한다.
- 하위 계층에서 처리되지 않은 예외는 바깥 계층으로 전파되어 각 계층의 오류 훅에서 관찰될 수 있다.
- HTTP adapter는 전파된 `Error`를 해당 상태 코드로 응답하고, 그 밖의 예외는 세부 내용을 노출하지 않는 일반 500 응답으로 변환한다.
- 현재 구조에서는 오류 훅이 오류를 관찰할 수는 있지만, 요청·오류 맥락에 따른 사용자 정의 응답으로 전환할 수 없다.

## 범위

### 포함

- 세 종류의 기존 요청 오류 훅 반환 계약을 `Optional[Response]`로 확장한다.
- 오류 훅이 반환한 `Response`를 정상 요청 응답처럼 적절한 바깥 처리 계층과 HTTP adapter로 전달한다.
- `None` 반환 시 현재의 오류 훅 실행, 예외 전파 및 adapter 기본 응답 동작을 유지한다.
- 오류 훅 반환값, 훅 실행 순서, 오류 훅 실패 및 이미 시작된 응답 writer에 대한 동작을 일관되게 정의하고 검증한다.
- 오류 처리 운영 안내를 별도 한국어·영어 상세 매뉴얼로 분리하여 작성하고, 두 문서 진입점에서 연결한다.
- 생명주기 매뉴얼에서는 오류 처리 상세를 중복하지 않고 별도 오류 처리 매뉴얼로 안내한다.

### 제외

- `ApplicationRequestError` 또는 `Application.on_request_error`의 신규 도입. 둘 다 이미 존재한다.
- 요청 객체를 생성하기 전에 발생한 오류를 Application 오류 훅에 전달하는 기능.
- 헤더나 응답 본문을 보낸 뒤 발생한 스트리밍·네트워크 오류를 새 HTTP 응답으로 교체하는 기능.
- Application 시작·종료 및 Extension 시작·정리 훅의 오류 계약 변경.
- 모든 오류 훅이 `None`을 반환한 경우 adapter가 사용하는 기존 기본 오류 응답 정책 변경.

## 기능 요구사항

### FR-1. 오류 훅 반환 계약

`RequestRunnerRequestError`, `ExtensionRequestError`, `ApplicationRequestError`는 기존 호출 인자 `(request, error)`를 유지하고 `None` 또는 `Response`를 반환할 수 있어야 한다. 공개 타입 주석은 `Optional[Response]`로 표현한다.

### FR-2. 미처리 오류의 전파

오류 훅이 `None`을 반환하면 그 계층은 오류를 처리하지 않은 것으로 간주해야 한다. 같은 계층에 다음 오류 훅이 있으면 등록 순서대로 실행한다. 그 계층의 오류 훅이 모두 `None`을 반환하면 원래 예외를 다시 발생시켜 상위 처리 계층이 계속 처리할 수 있게 한다.

### FR-3. 오류 응답의 확정

각 처리 계층에서 정상 응답 생성, 그 계층이 소유한 응답 검증 및 해당 계층의 응답 훅 실행을 먼저 수행한다. 이 과정에서 예외가 발생하면 같은 계층의 오류 훅 처리로 전환한다. 따라서 오류 훅은 해당 계층의 정상 응답 경로가 실패했을 때 사용하는 마지막 대체 경로이며, 정상 응답 훅과 오류 훅은 서로 다른 경로로 실행해야 한다. Application이 응답을 adapter에 전달한 뒤 발생한 직렬화·네트워크·전송 오류는 Application 요청 처리 경계 밖의 오류이며, Application 오류 훅 대상에 포함하지 않는다.

한 처리 계층에 여러 오류 훅이 등록된 경우 등록 순서대로 호출해야 한다. `None`을 반환한 훅은 오류를 처리하지 않은 것이므로 다음 훅을 계속 호출한다. 처음 `Response`를 반환한 훅의 응답을 해당 오류 처리 결과로 채택하고, 그 뒤 같은 계층에 남아 있는 오류 훅은 호출하지 않는다. 이 훅이 처리한 원래 예외는 완료된 것으로 간주하며, 같은 원래 예외를 처리하기 위해 더 바깥 계층의 오류 훅을 호출하지 않는다. 이 `Response`는 이미 오류가 난 계층의 응답 훅에 다시 넣지 않고 정상 응답으로 바깥 계층에 반환한다. 바깥 계층은 자체 정상 응답 검증과 응답 훅을 실행한다. 이 바깥 정상 응답 처리 중 새로운 예외가 발생하면 해당 바깥 계층의 오류 훅을 실행한다. 처리된 원래 예외를 다시 발생시키거나 adapter의 기본 오류 응답으로 대체하지 않는다.

같은 계층의 모든 오류 훅이 `None`을 반환한 경우에만 해당 예외를 상위 처리 계층으로 전파한다. 상위 계층에서도 정상 응답 처리에 실패할 때 해당 상위 계층의 오류 훅으로 전환하며, 최초로 `Response`를 반환한 계층에서 해당 예외의 오류 처리를 끝낸다.

### FR-4. 계층별 응답 처리

- `RequestRunner`의 응답 생성·검증·응답 훅에서 발생한 예외는 `RequestRunner` 오류 훅으로 전달해야 한다. 그 오류 훅이 `Response`를 반환하면 RequestRunner 응답 훅을 다시 실행하지 않고, Application의 정상 응답 처리로 전달해야 한다.
- `Extension`의 요청·호출·응답 훅에서 발생한 예외는 Extension 오류 훅으로 전달해야 한다. 그 오류 훅이 `Response`를 반환하면 Extension 응답 훅을 다시 실행하지 않고, 외부 RequestRunner 및 Application의 정상 응답 처리로 전달해야 한다.
- Application 응답 생성·검증·응답 훅에서 발생한 예외는 Application 오류 훅으로 전달해야 한다. 그 오류 훅이 `Response`를 반환하면 이미 실패한 Application 응답 훅을 다시 실행하지 않고 adapter로 전달해야 한다.
- 오류 응답이 바깥 계층의 정상 응답 처리에서 검증 또는 응답 훅 오류를 일으키면 그 오류는 해당 바깥 계층의 오류 훅에서 처리해야 한다. 이미 오류를 처리한 안쪽 계층의 오류 훅은 재호출하지 않는다.
- Application이 응답을 adapter에 전달한 뒤 발생한 직렬화·네트워크·전송 오류는 Application 오류 훅으로 되돌아가 재처리하지 않고 adapter·transport의 오류 처리 경로를 따른다.

### FR-5. 반환값 검증

오류 훅의 반환값은 `None` 또는 `Response`여야 한다. 그 밖의 값을 반환하면 명시적으로 `TypeError`를 발생시켜 계약 위반을 알린다. 반환값 오류를 무시하거나 정상 응답으로 간주하지 않는다.

### FR-6. 오류 훅 자체의 실패

오류 훅에서 예외가 발생하면 해당 훅의 예외를 호출자에게 전파해야 하며, 원래 처리 중이던 예외를 예외 체인에서 확인할 수 있어야 한다. 오류 훅에서 예외가 발생한 뒤 같은 계층의 남은 오류 훅을 실행하지 않는다.

### FR-7. 이미 시작된 직접 출력

오류 발생 시 응답 writer가 이미 시작된 경우 새 `Response`를 이용해 상태 코드나 본문을 교체할 수 없다. 이때 응답 교체를 성공한 것으로 처리하지 않고 기존 전송 실패 동작을 유지하며, writer와 응답 자원은 기존 소유권·정리 규칙을 따라야 한다.

### FR-8. 미처리 오류의 기본 응답

모든 해당 오류 훅이 `None`을 반환하면 기존 adapter 동작을 유지해야 한다.

- `Error` 하위 예외: 예외가 지정한 HTTP 상태 코드와 기존 오류 본문을 사용한다.
- 그 밖의 예외: 일반 500 응답을 반환하고 예외의 민감한 세부 정보를 클라이언트에 노출하지 않는다.

## 호환성 및 제약

- 기존에 `None`을 반환하는 오류 훅은 수정 없이 동작해야 한다.
- 오류가 발생하지 않는 요청의 요청 훅·응답 훅·라우팅·응답 전송 동작은 변경하지 않는다.
- 공개 오류 훅의 인자 순서와 수는 유지한다.
- 오류 응답은 일반 `Response`와 동일한 전송 및 자원 정리 규칙을 따른다.
- 응답 전송을 시작한 뒤에는 오류 응답으로 상태 코드나 본문을 변경할 수 없다.

## 인수 기준

- [ ] 세 오류 훅 계약의 반환 타입이 `Optional[Response]`로 명시되고 `(request, error)` 인자는 유지된다.
- [ ] 한 계층에 여러 오류 훅이 등록된 경우 등록 순서대로 호출된다. 앞선 훅이 `None`을 반환하면 다음 훅이 실행된다.
- [ ] 복수 오류 훅 중 최초로 `Response`를 반환한 훅의 응답이 채택되고, 같은 계층의 후속 훅은 호출되지 않는다.
- [ ] 최초 `Response`를 반환한 훅이 처리한 원래 예외에 대해 더 바깥 계층의 오류 훅이 호출되지 않고, 해당 응답이 adapter 기본 오류 응답으로 대체되지 않는다. 단, 그 응답을 처리하는 바깥 계층의 정상 응답 경로에서 새 예외가 발생하면 그 바깥 계층의 오류 훅이 실행된다.
- [ ] 한 계층의 모든 오류 훅이 `None`을 반환하면 원래 예외가 상위 계층으로 전파되고, 그 계층의 여러 오류 훅이 모두 한 번씩 등록 순서대로 실행된다.
- [ ] 응답 생성·응답 검증·응답 훅 중 발생한 예외가 해당 범위의 오류 훅에 전달되고, 그 범위의 정상 응답 훅은 오류 응답에 재실행되지 않는다.
- [ ] 오류 응답은 바깥 계층의 정상 응답 경로를 통과하며, 바깥 계층의 응답 처리에서 새 예외가 발생하면 해당 바깥 계층의 오류 훅으로 전환된다.
- [ ] 오류 훅은 계층별 정상 응답 경로의 최종 fallback으로 동작하며, 처리 완료 후 동일 계층의 정상 응답 훅 또는 오류 훅을 재귀적으로 다시 실행하지 않는다.
- [ ] Application이 응답을 adapter에 반환한 뒤 발생한 직렬화·네트워크·전송 오류는 Application 오류 훅에 다시 진입하지 않는다.
- [ ] 오류 훅이 잘못된 타입을 반환하면 `TypeError`가 발생하고, 오류 훅이 예외를 발생시키면 해당 실패와 원래 오류의 예외 체인을 확인할 수 있다.
- [ ] 오류가 난 계층의 응답 훅은 오류 응답에 다시 실행되지 않으며, 외부 계층의 정상 응답 훅은 해당 계층까지 응답이 반환되는 경우 기존 순서대로 실행된다.
- [ ] writer가 이미 시작된 상황에서 오류 응답을 교체하지 않으며, 기존 직접 출력·스트리밍 오류 동작을 보존한다.
- [ ] 모든 오류 훅이 `None`을 반환할 때 `Error`의 기존 상태 코드 응답과 일반 예외의 기존 500 응답 및 민감 정보 비노출이 유지된다.
- [ ] 기존 `None` 반환 오류 훅과 정상 요청 경로의 동작이 회귀 테스트로 확인된다.
- [ ] 오류 처리 운영 상세가 별도 `ErrorHandling.md`와 `ErrorHandling.en.md`에 작성되고, 두 문서는 오류 훅 반환 계약, 계층별 우선순위, 기본 오류 응답, 운영상 관찰·보안 고려사항, 스트리밍 제약 및 예제를 상응하는 범위로 설명한다.
- [ ] 구현 시 기존 `docs/LifecycleAndErrors.md`와 `docs/LifecycleAndErrors.en.md`의 파일명을 각각 `docs/Lifecycle.md`와 `docs/Lifecycle.en.md`로 변경한다. 해당 문서는 생명주기와 정상 요청 훅 실행 흐름에 집중하고, 오류 처리 세부사항은 별도 매뉴얼로 연결한다.
- [ ] 한국어·영어 `docs/README` 진입점에서 오류 처리 매뉴얼을 별도 주제로 소개하고 링크한다.
