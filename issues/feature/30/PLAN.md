## 수행 순서

### 1. 인수 기준에 대응하는 테스트 추가

선행 조건은 확정된 요구사항과 작업 브랜치의 일치다.

- 기존 `WriterTests`의 writer 생성 방식과 `subTest` 패턴을 사용한다.
- 단일 줄, 빈 문자열, 비ASCII 문자열, 혼합 개행, 중간 빈 줄 및 마지막 줄바꿈의 예상 바이트를 독립적인 기대값으로 작성한다.
- 개행 다음의 `data:`·`event:`·`id:`·`retry:`가 모두 주석 내용으로 남는지 확인한다.
- `ResponseWriter` 직접 전달, `StreamWriter`, `ChunkedStreamWriter`를 각각 검증한다.
- write·flush 호출을 관찰할 수 있는 테스트용 출력 객체로 호출 순서와 실패 전파를 검증한다. 제품 코드에 관찰용 기능은 추가하지 않는다.
- 시작 전·종료 후·실패 후 호출과 이벤트 → 주석 → retry → 이벤트 순서를 검증한다.
- 기존 직접 출력 통합 테스트를 활용해 일반·chunked 경로에서 handler 반환 전 주석을 읽을 수 있는지 확인한다. 별도 서버 테스트 기반은 만들지 않는다.
- 새 테스트를 먼저 실행해 주석 API 미구현으로 실패하는지 확인한다. 환경·의존성 문제를 기능 미구현의 증거로 기록하지 않는다.

### 2. 주석 전송 API 구현

선행 조건은 1단계의 테스트 작성과 미구현 상태 확인이다. 관련 요구사항은 R1~R4다.

- 기존 메서드 형식에 맞춰 `comment(self, text: str) -> None`을 추가한다.
- CRLF·CR을 LF로 정규화하고 LF 기준으로 나눠 모든 줄 앞에 `: `를 붙인다.
- 마지막 빈 줄을 포함한 전체 전송 단위를 UTF-8 바이트로 인코딩한다.
- 기존 `self.writer.write()` 이후 `self.writer.flush()`를 호출한다.
- 상태 검사, HTTP chunk framing 및 오류 처리는 하위 writer에 맡긴다. 예외 처리·재시도·기본 메시지·새 추상화는 추가하지 않는다.
- 1단계 테스트를 다시 실행하고 기존 SSE·출력 관련 테스트를 함께 검증한다.

### 3. 상세 매뉴얼 갱신

선행 조건은 2단계 구현과 관련 테스트 통과다. 관련 요구사항은 R5다.

- 한국어·영어 SSE 절에 공개 메서드와 `begin()` 이후 주석을 보내는 예시를 추가한다.
- 연결 유지 목적의 반복 호출은 애플리케이션 책임이며 자동 타이머가 없음을 설명한다.
- 즉시 flush와 실제 클라이언트 수신·프록시 버퍼링·유휴 연결 유지 보장을 구분한다.
- 지속 연결 예시에서 이벤트 사이에 주석을 보내는 사용 흐름을 설명하되 불필요한 스케줄러 구현은 넣지 않는다.
- 기존 SSE 절에 추가하는 범위이므로 새 매뉴얼 파일이나 도식은 기본적으로 추가하지 않는다. 루트 README 요약의 변경 필요성은 실제 사용자 영향에 따라 확인한다.

### 4. 완료 검토와 기록

선행 조건은 2~3단계 완료다.

- 아래 검증표의 모든 인수 기준을 실제 결과에 대조한다.
- 의미 있는 구현 단계는 `implements/`에, 테스트·문서화 등 구현 외 단계는 `tasks/`에 진행 중 기록한다. 각 기록은 실제 수행 시 생성하며 계획을 완료 결과로 기록하지 않는다.
- 구현 결과는 `IMPLEMENTS.md`에 정리하고 기존 [작업 결과](./TASKS.md), [이슈 README](./README.md) 및 이 계획의 상태를 갱신한다.
- 매뉴얼 반영을 확인한 뒤 이슈의 `CHANGELOG.md`에 고객 관점의 API 추가·사용법·제약을 작성한다.
- 상대 링크, 개인 절대 경로 미포함, 변경 범위 및 임시 파일 혼입 여부를 확인한다.
- 커밋·푸시·병합·이슈 종료는 별도 요청 없이 수행하지 않는다.

## 인수 기준별 검증

| 기준 | 검증 방법 | 통과 조건 |
| --- | --- | --- |
| AC1 | 단일 줄·빈 문자열·비ASCII 입력의 출력 바이트 비교 | UTF-8 내용과 `\n\n` 경계가 명세와 정확히 일치 |
| AC2 | CRLF·CR·LF·혼합 개행과 빈 줄 조합을 `subTest`로 비교 | 모든 줄과 마지막 빈 줄이 명세대로 보존 |
| AC3 | 개행 뒤에 각 SSE 필드 이름을 넣은 입력 검증 | 각 줄이 `: `로 시작하며 독립적인 필드 줄이 없음 |
| AC4 | 직접 전달·일반·chunked 출력 바이트, 호출 순서 및 기존 통합 테스트 확인 | 동일한 SSE 본문, 올바른 chunk 크기·종료, 성공한 write 직후 flush, handler 반환 전 수신 |
| AC5 | write와 flush에 각각 실패를 주입 | 원래 예외 전파, write 실패 시 flush 미호출, 기존 실패 상태와 후속 쓰기 차단 유지 |
| AC6 | 시작 전·종료 후 상태 오류와 이벤트·주석·retry 혼합 출력 확인 | 기존 상태 계약 유지, 필드와 프레임 경계 불변, 주석에 의한 ID·retry 필드 추가 없음 |
| AC7 | 기존 writer·SSE 테스트 실행 | 기존 이벤트 인코딩·검증 및 일반·chunked 출력 테스트 통과 |
| AC8 | 한국어·영어 매뉴얼과 구현 대조 | 시그니처·예시·애플리케이션 책임·보장 범위 일치 |

### 테스트 실행 범위

추가한 테스트만 먼저 실행해 실패·성공을 확인한 뒤 관련 파일로 확대한다. 아래는 저장소 루트에서 프로젝트 의존성이 준비된 Python으로 실행할 예정인 회귀 검증 명령이다.

```shell
python -m unittest discover -s tests -p test_writers.py
python -m unittest discover -s tests -p test_sse.py
```

관련 테스트 실패나 확인된 영향이 다른 영역으로 이어질 때만 해당 테스트로 범위를 확대한다. 문서 검증을 위해 새 도구를 설치하거나 전체 테스트를 선행 실행하지 않는다.

## 호환성과 남은 조건

- 기존 API의 변경 없이 메서드를 추가하므로 설정·데이터 마이그레이션은 없다.
- 새 기능은 호출한 경우에만 사용하며 별도 feature flag를 추가하지 않는다.
- 변경을 되돌려야 하면 이번 작업의 메서드·테스트·매뉴얼 변경만 대상으로 판단하고 기존 사용자 변경은 보존한다.
- 병합 대상 미지정은 로컬 구현·검증을 막지 않는다. 실제 병합을 요청받는 시점에 확인한다.
- 선행 분석의 기존 테스트 5개 통과는 기준 동작 확인일 뿐 신규 기능이나 이 계획의 완료를 의미하지 않는다.
